# Lessons learned

## Jetson Orin performance (issue #2, 2026-09-26)

- **Pin the clocks before measuring anything.** Under a bursty real-time load, `nvhost_podgov` keeps the Orin GPU at 408–510 MHz of 1020, and `schedutil` drops CPU cores to 729 MHz. Every model then takes about 2× its standalone time. Run `sudo jetson_clocks`; it resets on reboot. Isolated benchmarks saturate the GPU and hide this.
- **Compare in-app stage time with isolated time.** A large gap means the time goes outside the model: clocks, contention, or Python glue.
- **Detection count moves FPS more than code changes do.** Each detected body adds a face run and a body run, about 9 ms. Log detections per frame next to timings, and compare old and new code back to back in the same scene. An early "15 → 27 FPS" result turned out to be the scene changing, not the fix.
- **A slow TensorRT build is not a hang.** The person detector's build "hung" for 300+ s, then failed after about 6 min with `Layers missing empty tensor support`. Give builds a 10-minute timeout and read the error.
- **Split models with built-in NMS by op type.** ORT's `trt_op_types_to_exclude` works per op type, not per node. Excluding the op types that occur only after NMS, plus `trt_min_subgraph_size`, keeps the backbone in TensorRT and puts the post-processing on CUDA/CPU. `tools/orin_bench/bench_models.py post-ops` lists those types.
- **Python loops over landmarks are expensive on the Orin's CPU.** Numpy scalar indexing in a 478-point loop took 4.3 ms per face. Vectorize with `.tolist()`.
- **The "different models of devices" TensorRT warning was harmless here.** Rebuilt engines ran at the same speed; check this rather than assuming.
- **Measure GPU clocks from sysfs** (`/sys/class/devfreq/17000000.gpu/cur_freq`). tegrastats on this JetPack shows only GR3D percent.
- **Tooling:** `devops_task` commands that run past its time limit report FAIL with no output but keep running on the remote host. Background long jobs with `nohup ... &` and poll a log, otherwise duplicate runs pile up and compete for the GPU.

## False positives (issue #3, 2026-09-26)

- **Save the raw frame, not just the overlay.** Overlay frames have meshes drawn on the very crops you want to re-score. `--dump-detections` saves both.
- **Replay offline before choosing a threshold.** Cropping dumped boxes from raw frames and running the landmark model on the laptop gave score ranges for real vs false detections in minutes, without touching the Orin.
- **Label by eye with a contact sheet.** A grid of crops with their scores printed on each tile made it obvious which scores were real faces. Labelling by position broke as soon as people moved.
- **Check what a model already outputs.** The face landmark model had a face score all along (`Identity_1`); the code only read the landmarks.
- **Crop padding changes model scores a lot.** With 25% padding, real faces scored near the decision boundary; without padding they scored far above it.
- **Some false positives can't be fixed per frame.** A static lamp scores the same as a seated person on every signal the models give. It needs information across frames (tracking, calibration).
- **Lighting changes the false positives.** In bright sun the ball and lamp were not detected at all. Test in the light you will run in.

## Keeping the Orin recoverable (2026-09-26)

- **An agent copying a whole repo tree destroyed the Orin's Python environment.** The laptop's `env/` (Python 3.12) overwrote the Orin's (Python 3.10). `env/` is not in git, so nothing recorded how it was built. Deploy through git only, and never copy directories to the Orin.
- **pip's HTTP cache can hold wheels you can no longer find.** The original onnxruntime-gpu wheel was recovered from `~/.cache/pip/http` by searching cached responses for the zip header. Keep wheels you install from outside PyPI.
- **Snapshot before changes, automatically.** `tools/orin_setup/snapshot.sh` runs from the pre-push hook; hard links keep snapshots cheap, and read-only directories stop `rm -rf`. See `tools/orin_setup/README.md`.
- **pip will quietly upgrade numpy.** Installing onnx pulled numpy 2, which broke the OpenCV build compiled against numpy 1.x (`_ARRAY_API not found`).
- **Check `pgrep -f` isn't matching itself.** Over ssh, `pgrep -f 'python poser'` matched the ssh command line and reported a run that had never started. Use `ps -eo args | grep '^[p]ython poser'`.

## Tracking, props and faces (issues #6/#7, 2026-09-27)

- **Get labels from the people in the room, and make them easy to read.** Thresholds chosen from unlabelled runs were wrong twice; one labelled 60 s run was worth more than several unlabelled ones. Track numbers must be readable from ~10 ft (text ~1/14 of frame height) and centred on the box: a top-left label next to a lamp's label was read as the lamp's number.
- **A test that needs people must be on the screen.** Two headless face-crop tests ran while nobody was performing, and their result was the opposite of the real one (padding looked best; with people facing the camera the unpadded crop kept 37% of faces vs 0-5% padded). Show the app or a big "TEST RUNNING – do X" with a countdown.
- **Frame-to-frame movement measures jitter, not people.** The pose model's skeleton on a lamp shakes more than a still person's. Measure over a longer window: the 90th-percentile distance of the box centre from its median over ~10 s separated dancers (0.08-0.93 of box height) and a person standing still (0.055) from a prop (0.037). People sitting very still (0.025) look like props.
- **Head-box rate and face scores didn't separate props either.** The lamp got a false head (0.47) on top of it; head and body scores of props and people overlap. Dancers' faces score low (logit < 8) from blur and turns.
- **Fixed ignore zones work until the unit moves.** A venue file of prop boxes removed the lamp and chair, but the owner moves the unit and the light changes through the day; the filter has to learn by itself (`--drop-still`).
- **A box that flips between a small and a big size breaks velocity prediction.** The centre jump looks like movement, the prediction misses the next box, and a new ID starts while the old track is alive. Fall back to the last box when the predicted box doesn't match; revive a lost track when half of the smaller box overlaps.
- **A higher-scoring box inside a person's box can be a duplicate.** A 0.56 box on part of a person, 90% inside their 0.51 box, took their head. When one box is >= 80% inside another, keep the one the head fits.
- **Faces work for the dancer; nobody else may be facing the camera.** With one dancer and kids doing homework, the dancer's face was found in 69-88% of frames and the kids' in 0-7%. Ask who was where before tuning on a "low" number.
- **Tooling:** `pkill -f poser.py` over ssh kills its own `bash -c`; kill by PID. A devops call the owner rejected still ran twice. `Failed to create CaptureSession` means another process (often the service) holds the camera. Killing the service's process with TERM exits 0, so `Restart=on-failure` leaves it stopped.

## Smoothing, pose crops and hands (2026-10-11)

- **Jumpy skeletons came from the crop, not only the detector.** The pose model (BlazePose GHUM) expects MediaPipe's crop: a square centred on the hips, sized from its own alignment points (33, 34), rotated upright, black outside the frame, taken from the previous frame's landmarks. Given the person box letterboxed instead, it drew a skeleton too small for the person (low shoulders, short arms) and lost the pose in a third of frames. With MediaPipe's crop the error against MediaPipe fell from 0.22 to 0.086 shoulder widths, with no FPS change.
- **Measure against a reference before changing a model's input.** A 10 s laptop recording and MediaPipe 1.1 (`mediapipe` in a separate venv) as the reference turned "looks bad" into numbers in minutes, and checked each fix through the app's own code. Kept local in `testdata/pose-eval/` (git-ignored; it shows a person).
- **Check which output is which.** The hand model's outputs are landmarks, presence, handedness; the code read handedness as presence, so hands were kept by side and one hand was rarely found. A crop with no hand in it shows which output is presence (0.000 vs 0.3).
- **Crop hands from the body, then from the hand itself.** The detector's hand boxes found 40% of hands on the laptop and almost none at the Orin's distance. Crops from the pose wrist/index/pinky, then from the hand's last landmarks (MediaPipe Holistic), found 92%. Hands MediaPipe "missed" that we found were real (blur, frame edge): look at them before calling them false.
- **One Euro smoothing on landmarks, not on crops.** Smoothing the landmarks per person (speed in object sizes per second) made the skeleton steady without visible lag, at 1.3 ms per frame on the Orin (still ~31 FPS). Smoothing the head box would move the face off-centre in its crop, and the face model loses faces when that happens (issue #6/#7).
- **Log why a new ID starts.** `[NEW-ID]` names the nearest old track (live/lost, distance, size, overlap). On the first run it showed two boxes on one person (`live missed=0 overlap 0.4`), not a lost person — a cause no one had guessed.
- **Small artefacts matter to the viewer.** The pose model's finger points (17-22) drawn on top of the hand model's hands looked wrong; the body now stops at the wrists.

## Speed on the Orin: replay a clip, change one thing at a time (2026-10-11)

- **Benchmark on a recorded clip, not live.** FPS depends on who is dancing; a 60 s raw clip of two people (`tools/orin_bench/record_video.py`, replayed with `poser.py --video`) gives runs that repeat within 0.2 FPS. `tools/orin_bench/clip_bench.sh` runs it with the service's arguments.
- **Check the benchmark's own time first.** The first replays showed 23 FPS; 10 ms of every frame was the clip reader (a sync 6 MB read per frame, and the page cache it filled made a later GPU allocation fail with NvMap error 12). Reading ahead in a thread and dropping frames from the cache gave the real baseline: 27.6 FPS.
- **Interleave A/B runs.** Measured in sequence, reusing crop buffers looked 0.6 FPS worse; interleaved with its control it was 0.7 FPS better. Steps run minutes apart drift.
- **What helped (two people, `--pipeline`):** drawing frame N while frame N+1's models run (+2-3 FPS; drawing is ~8 ms the GPU used to wait for), shrinking the frame before converting it to RGB for the person detector (+1.4), reusing crop buffers (+0.7), one face-model run for all faces (+2.1). 27.6 -> 30.5 FPS; 24.8 without `--pipeline`.
- **Give TensorRT a fixed batch range.** A model with a dynamic batch rebuilds its engine (~6 min on the Orin, app frozen) the first time a new batch size appears; set `trt_profile_min/opt/max_shapes`.
- **A half-busy GPU and CPU means waiting, not too little power.** At 21 FPS the GPU was ~60% and the CPU ~50% busy at ~20 W of 35 W: each crop and model run waits for the previous one. On the Orin the CPU and GPU share memory, so copies are cheap; the waits at each download and model run are where the time goes.
- **`jtop` reports the system OpenCV (4.8.0, no CUDA).** The app's venv loads the CUDA build (4.10.0) through `00-opencv-cuda.pth`; check with the venv's python, not jtop.
- **Profile before guessing (`nsys`, `py-spy` on the clip).** The GPU computed only ~23% of the time: ~900 kernel launches a frame at ~12 us each, about the CPU time of one launch, plus waits at every crop download and model input copy. Keeping crops on the GPU (I/O binding to a fixed continuous buffer) and letting TensorRT replay each model as a CUDA graph (`trt_cuda_graph_enable`) took hand + body from 12.4 to 8.8 ms a frame: 30.8 -> 34.5 FPS with two people, same outputs.
- **OpenCV and ONNX Runtime use different CUDA streams.** OpenCV works on the default stream; ONNX Runtime's stream doesn't wait for it, and an upload from ordinary CPU memory can return before it lands. Without a wait before each run, 8 of 60 test runs read a stale input. A CUDA graph also replays its first run's addresses: one buffer set per model.
- **Compare a fast path with the same engine, not a different precision.** TensorRT FP16 and an FP32 reference differ by up to 15 model pixels on noise input; against the same FP16 engine the GPU path matched to 0.001.
- **Faces and detector on the GPU too.** Face crops cut on the GPU into one bound batch-of-2 buffer, replayed as one CUDA graph (2 faces: 6.4 -> 2.9 ms); detector input prepared on the GPU (5.4 -> 4.4 ms; no graph, part of it runs outside TensorRT). Two people, `--mirror --pipeline`: 32.6 -> 35.6 FPS. A second CUDA graph for another batch size in the same session (`gpu_graph_id`) gave wrong outputs with no error: keep one fixed batch per graph.
- **A benchmark is only valid with nothing else on the GPU.** One rerun showed everything 30% slower: the service had been restarted and ran alongside. Check `systemctl is-active party-pose` and `pgrep` before trusting numbers.
- **The method and every technique with its measured gain are collected in [orin-performance-tuning.md](orin-performance-tuning.md)** — start there for the next tuning attempt.

## Flicker, faces, hands and finding dancers at the new spot (issue #13, 2026-10-11 to 2026-10-17)

- **Count what the viewer sees before changing it.** A `[FLICKER]` line at the end of a `--video` run counts, per track and part (body, face, each hand), gaps of 1-5 frames between drawn frames. Ghosts (a missing part's last smoothed result redrawn at 80/60/40/20%) took the two-people clip from 569 to 158 blinks with no FPS change. What is left are absences longer than the fade.
- **The camera is at its limit indoors.** At the new spot the IMX219 ran at gain 170 of 171 and 30 ms exposure (the whole frame time at 30 fps) in every recording, day and evening. Still people were found in every frame; moving dancers were blurred and the person detector found them in 10-50% of frames. `tools/orin_bench/record_video.py` now logs gain, exposure and brightness once a second into each clip's `.json`.
- **The detector's own limits come first.** The YOLOX body/head/hand model has NMS inside it: score 0.25, IoU 0.4, at most 20 boxes per class. An app threshold below 0.25 does nothing. On the evening three-dancer clip it gave about 1 body box per frame for 3 dancers, and a big person close to the camera (box 0.75-0.9 of the frame height, cut off at the edges) had a box in only ~21% of frames. Lower thresholds can't help when the boxes are not there.
- **A body always has a head: crop the face from the pose.** The face model used to run only on the detector's head box, which is missing in about a third of frames. A square around the current pose's face points (0-10) at 2.0x their spread drew a face in 94% of body frames at the new spot (head box: 70-77%). Head box first, switching crops after a miss, and the previous frame's pose (dancers move too far in one frame) were all clearly worse. Check what a summary line counts: one "head box, else pose" line counted a face found by either crop, and predicted the wrong result.
- **Lost hands are the hard part.** A hand followed from its own last landmarks is found in 80-89% of frames, also over the body. Once lost, a crop from the pose's wrist/finger points finds it in ~20% (over the torso ~10%): with arms across the body the pose's wrist point sits up the forearm and the hand is outside the crop (seen on crops). Fifteen other pose-based crops (finger, forearm and shoulder-sized, a 5-crop search) never got over-torso hands above ~36%. Lowering the 0.5 hand threshold adds ~5%: misses score below 0.1.
- **Follow a found person with the pose model, as MediaPipe does.** The detector only finds people; each frame the pose runs on the crop from the person's previous pose, with or without a detector box, and detector boxes mostly inside a followed person's pose box start no second track. One-person clips: body drawn in every frame, 0 body and face blinks, hands about twice as often, never a second skeleton (before: two skeletons on one dancer). Downside: a smaller dancer next to a followed one can be taken for part of them.
- **Measure where time goes before blaming a model.** Following looked like an extra pose run per frame (-2.3 FPS); a count of model runs showed one per person drawn. The time was `Track.is_still()` working out the spread of 300 box centres up to 3 times per track per frame; computing it once per new box gave most of it back.
- **People sizes at the new spot (frame height 1080):** dancers 0.56-0.89 of the frame height, a child close to the camera 0.47, the lamp at the right edge narrow (width/height 0.32, detector score ~0.45, a false head on top, a face in 2% of frames, still). `--min-body-height 0.40` drops people far back without dropping the child.
- **A hand stays with its own person.** A hand chained from its last landmarks can jump onto another person's hand; keeping only hands whose wrist is within 0.5 shoulder widths of the person's own pose wrist rejected 1.9% of found hands (median distance 0.08).
- **Check the replay's own reading of the clip.** One batch showed 8 FPS on screen: the `capture` stage went to ~100 ms per frame for two minutes (the disk read 1.4 GB/s when checked). A run counts only if `capture` stays at ~2 ms.
- **Replay FPS vs live FPS.** Live the camera gives 30 fps; replays run as fast as the models allow. Two people replay at ~35 FPS; four people at ~23, which shows on screen live. The goal for the party is >= 30 live with 3-4 dancers.
- **Live tests with the family:** show what to do and a seconds counter on screen (`--test-label`), ask who was in view and where (one "two skeletons" result was one dancer; a "three dancer" run was after the kids had left), and record the scene (`record_video.py`) so every later change is replayed on it instead of asking people to dance again.
- **Other GPUs for accuracy runs.** Detector and crop accuracy is nearly the same on any NVIDIA GPU: half-size lossless copies of the Orin clips (`testdata/clips_half/`) run on the RTX 3060/5080 rig and the DGX Spark (ONNX Runtime GPU; the Spark needs `onnxruntime.preload_dlls()`). Only speed has to be measured on the Orin, one benchmark at a time (`flock /tmp/orin_bench.lock`).
- **Small things that took time to find out:** the Orin's `/tmp` is cleared when it restarts (test scripts were gone after the move); the Orin moved to Wi-Fi at 192.168.2.167; `git commit -a` picked up an unrelated uncommitted README change, so add files by name.

## Speed and smooth figures for the party (issue #13, 2026-10-18)

All numbers and tables: `docs/issue-13-party-readiness.md`.

- **One replay at a time on every machine, not only the Orin.** Two measuring jobs ran 4-5 laptop replays at once: the laptop's quality numbers then varied by up to 1.5 pops/100 between identical runs and its FPS from 10 to 36. A lock (`flock /tmp/laptop_bench.lock`) fixed it. The rig (192.168.2.60) and the Spark can run model-only checks, but not the app: their OpenCV has no CUDA and the app calls `cv2.cuda` in ~57 places.
- **Load every model session before the first frame.** Sessions were loaded on first use, and with `--pose-batch`/`--hand-batch`/`--face-batch` each batch size has its own TensorRT session: the picture froze for 1-3 s the first time 3 or 4 people were in view, and `--video` timings counted the load (py-spy: 31% of the model thread in session creation; the person detector averaged 43 ms/frame over the first 60 frames, ~3 ms after). Loading them at startup gave three_dancers 26.9 -> 30.2 FPS in the replay, and no freeze live.
- **py-spy on the slowest clip found Python work, not model work.** A ghost face was moved by building 478 new Landmark objects every frame (~1.7 ms/frame with faces every 2nd frame): it is now moved when read. `Track.is_still()` worked out the spread of 300 box centres for every followed person every frame, because following gives a box every frame: once the 10 s window is full it is worked out every 10th box. Together +2 FPS, the same output.
- **Run hands and faces every 2nd frame per person** (`--hand-every 2 --face-every 2`; a person's face runs on the frames their hands skip). On a skipped frame the last result is drawn at full brightness, moved with the pose wrist or head. Fewer blinks than running every frame (fewer misses to ghost), drawn jitter the same. Every 3rd frame gives +1.5 FPS more, but the raw hand points step more between model runs.
- **The person detector is only needed for people not followed.** `--detect-every 3` runs it every 3rd frame while every live person was followed by their pose last frame, otherwise every frame; +1.2 FPS. Deciding after following (this frame's result) made the detector itself ~4.5 ms slower; deciding from last frame keeps it first.
- **Running the detector in parallel works but the Orin GPU is shared.** `--detect-ahead` (read and detect frame N+1 in its own thread) gave +1.0 FPS with a GPU copy of each frame (a GPU free waits for the whole device) and +1.8 with a ring of 6 preallocated frames; the per-person models then ran 25-35% slower. Not used with `--detect-every`.
- **What did not help:** the MediaPipe lite pose model (+0.5 FPS, 19% fewer hands drawn, more body pops); `--switch-ms`; OpenCV crops on their own CUDA stream instead of the default one (0.66 vs 0.72 ms per 4 crops); `--hold-joints` once scores are averaged; `--ghost-follow-wrist` (hands pop more).
- **Smooth figures:** `--score-smooth 0.05` (average joint presence over frames) cut body pops from 25-54 to 0.5-9 per 100 frames on every clip; One Euro beta 0.5 instead of 1.5 for body, face and hands lowered jitter for ~0.2-0.3 frames more lag; `--ghost-frames 8` cut face blinks (three_dancers 21 -> 4) and drew more hands.
- **Result (Orin replays, `--pipeline`, the service arguments in `tools/orin_setup/service/party-pose.env.example`):** three_dancers 23.7 -> 33.9 FPS with 2.90 of 3 people drawn (main: 0.76), three_people 20.0 -> 30.9 with 3.81 of 4 (main: 1.70), two_people 42, one person 60-66. Live the camera gives 30.
- **Replays with people from the first frame hid a live crash.** Live, with nobody drawn at first, the YOLOX tiny detector gave 0 rows for a few frames; the first frame with a box then failed in ONNX Runtime's output copy ("CUDA failure 1: invalid argument", every later run too), because the I/O binding kept the output of the empty first result. Fix: bind the output again before each run (no FPS change). It needed a clip where the first frames have no box (`testdata/clips/room_one_still`, one person sitting still, not drawn) and a test (`test_detector_finds_people_after_frames_with_nobody`). Every A/B now needs such a clip, and live smoke tests run unattended: the app must work with nobody in view.
- **The board throttles on over-current.** `soctherm_oc` counter `oc3_event_cnt` was 6733 after 8 h at MAXN_SUPER; each event lowers the clocks for a moment (a source of run-to-run FPS spread). NVIDIA's `nvpmodel_indicator` shows a desktop notification for each; banners are off for the show (`gsettings set org.gnome.desktop.notifications show-banners false`).
